# 需求正文的规范格式

- 状态：已接受
- 日期：2026-09-14

## 背景

正文此前由写入方自由拼装，出现了三类问题：标题前面的空行缺失、标题后面的空行多余；列表项之间夹空行会被渲染成松散列表，每项多出一段间距；事项编号跨一级主题连续（一、下面是 1，二、下面接着 2），读者会以为整篇是一条序列。这些差异只在渲染后可见，肉眼很难逐条发现。

## 决策

正文只有一种规范形态，由 `normalizeRequirementDescription` 在写入时强制：

```text
### 一、素材识别
1. 视频、音频素材在卡片中展示可辨识的类型标识。
2. 素材名称和关键类型信息同时可见。

### 二、卡片操作
1. 用户可从卡片进入预览。
```

- 一级主题 `### 中文序号、主题` 独占一行，前面固定一个空行，后面不留空行，它自己的有序列表从 `1. ` 开始，紧跟在标题下一行。
- 有序事项在一个主题内连续编号，**每个主题都从 1 重新开始**，不跨主题连续。
- 事项之间不留空行，正文块之间只保留一个空行；不允许两个以上连续空行，首尾不留空行。
- 文件层面同理：`## 章节标题`、图片、正文之间各保留一个空行。

管理器编辑、插件 MCP 写入与文件序列化共用这一条路径，因此新内容无需额外检查。

## 后果

正文在管理器和纯文本里都是同一种形态，渲染不会因为空行产生额外间距，编号与主题层级一致。存量 105 条需求已按此格式重写：内容、时间戳、图片归属均未改变。

标题的中文序号仍由内容决定：一个需求如果有多个 `##` 章节，章节内的主题序号可以从「二、」继续，规范化不会重排中文序号。
